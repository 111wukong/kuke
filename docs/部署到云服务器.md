# 部署到云服务器

面向**公网访问**的单机部署。默认读者是一台刚装好的 Ubuntu 22.04 / Debian 12 云主机。

> **先说结论：不要把 5180 端口直接开到公网。**
> 应用自己是纯 HTTP —— 学生的密码和会话 cookie 会明文过网。
> 正确结构是 `浏览器 → HTTPS → Nginx → HTTP → 应用(只监听回环)`。

---

## 0. 你需要准备什么

| 项 | 说明 |
|---|---|
| 云主机 | 2 核 2G 起步。**2G 是下限** —— 构建前端时 Node 会吃到 1G 以上 |
| 域名 | 必须有。Let's Encrypt 不签 IP 证书 |
| 安全组 | 放行 **80** 和 **443**；**不要**放行 5180 |
| 系统 | Ubuntu 22.04+ / Debian 12+。其他发行版命令自行替换 |

**1 核 1G 的机器会在 `npm run build` 阶段被 OOM 杀掉。** 如果只能用小机器，
在本地构建好 `web/dist` 再上传，或者加 swap。

---

## 1. 两条路线，选一条

### 路线 A：Docker（推荐）

环境一致、升级简单、不会污染宿主机。

```bash
# 装 Docker
curl -fsSL https://get.docker.com | sudo sh
sudo usermod -aG docker $USER && newgrp docker

# 取代码
sudo mkdir -p /opt/kuke && sudo chown $USER /opt/kuke
git clone https://github.com/111wukong/kuke.git /opt/kuke
cd /opt/kuke

# 建 .env —— compose 会读它做变量插值
cat > .env <<'EOF'
KUKE_EMAIL=teacher@your-school.edu
KUKE_PASSWORD=换成一个强密码
KUKE_USERNAME=张老师
EOF
chmod 600 .env

# 起服务
docker compose up -d --build
docker compose logs -f          # 看启动日志，确认没有报错
```

应用会监听 `127.0.0.1:5180`（只在本机可访问）。跳到第 2 步配 Nginx。

### 路线 B：systemd（不用 Docker）

```bash
# Node 22
curl -fsSL https://deb.nodesource.com/setup_22.x | sudo -E bash -
sudo apt-get install -y nodejs build-essential python3

# 建专用用户（不要用 root 跑服务）
sudo useradd -r -s /usr/sbin/nologin -d /opt/kuke kuke
sudo mkdir -p /opt/kuke /var/lib/kuke /etc/kuke
sudo chown kuke:kuke /opt/kuke /var/lib/kuke

# 取代码并构建
sudo -u kuke git clone https://github.com/111wukong/kuke.git /opt/kuke
cd /opt/kuke
sudo -u kuke npm ci
sudo -u kuke npm run build      # ★ 这一步最吃内存

# 环境变量
sudo tee /etc/kuke/env >/dev/null <<'EOF'
NODE_ENV=production
HOST=127.0.0.1
PORT=5180
KUKE_DB=/var/lib/kuke/kuke.db
TRUST_PROXY=127.0.0.1
KUKE_ALLOW_REGISTER=0
KUKE_EMAIL=teacher@your-school.edu
KUKE_PASSWORD=换成一个强密码
KUKE_USERNAME=张老师
EOF
sudo chmod 600 /etc/kuke/env && sudo chown root:root /etc/kuke/env

# 装服务
sudo cp deploy/kuke.service /etc/systemd/system/kuke.service
sudo systemctl daemon-reload
sudo systemctl enable --now kuke
sudo systemctl status kuke
```

## 2. Nginx + HTTPS

```bash
sudo apt-get install -y nginx certbot python3-certbot-nginx

# 用仓库里的模板，改掉域名和证书路径
sudo cp /opt/kuke/deploy/nginx.conf /etc/nginx/conf.d/kuke.conf
sudo sed -i 's/kuke\.example\.edu/你的域名/g' /etc/nginx/conf.d/kuke.conf

# 先删掉证书那两行（还没有证书），让 Nginx 能起来
sudo sed -i '/ssl_certificate/d' /etc/nginx/conf.d/kuke.conf
sudo nginx -t && sudo systemctl reload nginx

# 申请证书（certbot 会自动改回证书路径并加 443 配置）
sudo certbot --nginx -d 你的域名

# 自动续期（certbot 装包时通常已经配好 timer，确认一下）
sudo systemctl status certbot.timer
```

> **如果你用的是 Docker**，把 nginx.conf 里 `/assets/` 那个 location 删掉 ——
> 容器里的 `web/dist` 不在宿主机上，静态文件会走应用自己托管（也正常工作，
> 只是少一次 Nginx 直发的优化）。

### 改完之后一定要验的三件事

```bash
# 1. 浏览器打开 https://你的域名 —— 应该是登录页，且是绿锁
# 2. http://你的域名 —— 应该 301 跳到 https
curl -sI http://你的域名 | head -3

# 3. ★ 确认应用真的拿到了真实客户端 IP（不是 127.0.0.1）
curl -s https://你的域名/api/health
sudo journalctl -u kuke -n 30 | grep -i "ip"
```

第 3 条对应 `TRUST_PROXY`。**配错的后果是静默的**：
限流会把所有人当成同一个 IP，审计日志里所有登录都来自 127.0.0.1 ——
出事时查不到人，而系统看起来完全正常。

## 3. 首次登录

第一次启动时，如果数据库里没有教师账号，服务会用它建一个。
**不会打印随机密码** —— 因为你在环境变量里指定了 `KUKE_PASSWORD`。

用 `KUKE_EMAIL` / `KUKE_PASSWORD` 登录 → **立刻改密码** → 改掉环境变量里的值。

> 账号一旦存在，改环境变量**不会**重置它（启动服务不该覆盖别人改过的密码）。
> 忘了密码用：`node scripts/reset-password.mjs <email> <新密码>`

## 4. 收学生进来

生产环境**默认关闭自助注册**（`NODE_ENV=production` 时）。
不要为了图省事打开它 —— 那等于「任何人知道域名就能注册」。

正规流程：

1. 老师登录 → **班级** → 新建班级 → 拿到 8 位邀请码
2. **教师工作台 → 学生** → 批量建号（或让学生自己注册时填邀请码）
3. 把域名 + 邀请码发给学生

如果确实要开自助注册：`KUKE_ALLOW_REGISTER=1`，并在班级页把邀请码发出去。
注册接口要求邀请码有效，所以不会出现「陌生人注册了但不属于任何班」的孤儿账号。

## 5. 备份

**SQLite 是单文件，但它不是「cp 一下就行」。**
WAL 模式下最新的写入可能还在 `-wal` 文件里，`cp kuke.db` 会得到一个
缺了最近若干次提交的、看起来完全正常的库。必须让 SQLite 自己导。

```bash
# 手动跑一次
cd /opt/kuke
sudo -u kuke node scripts/backup.mjs --out /var/backups/kuke --keep 30

# 配成定时任务
sudo crontab -u kuke -e
# 加一行（避开整点）：
17 3 * * * cd /opt/kuke && /usr/bin/node scripts/backup.mjs --out /var/backups/kuke --keep 30 >> /var/log/kuke-backup.log 2>&1
```

脚本做三件事：`VACUUM INTO` 导出快照 → **打开它跑 integrity_check** → 轮转旧文件。
校验失败会把坏文件删掉并报错 —— 留着一个坏备份比没有备份更危险。

> **备份要放到另一台机器上。** 备份和数据库在同一块盘上，
> 盘坏了两个一起没。用 `rclone` / `ossutil` 同步到对象存储。

### 恢复

```bash
sudo systemctl stop kuke          # 或 docker compose down
sudo cp /var/backups/kuke/kuke-YYYYMMDD-HHMMSS.db /var/lib/kuke/kuke.db
sudo rm -f /var/lib/kuke/kuke.db-wal /var/lib/kuke/kuke.db-shm   # ★ 必须删掉旧的 WAL
sudo systemctl start kuke
```

**恢复时一定要删 `-wal` 和 `-shm`。** 留着的话 SQLite 会拿旧 WAL
去「重放」到新库上，结果是数据错乱 —— 而且不报错。

## 6. 升级

```bash
cd /opt/kuke
sudo -u kuke git pull
sudo -u kuke npm ci
sudo -u kuke npm run build
sudo systemctl restart kuke
```

Docker 版本：`git pull && docker compose up -d --build`。

**升级前先备份。** 数据库结构迁移（`server/src/db/migrate.js`）在启动时自动跑，
回滚旧版本不会自动撤销结构变更。

## 7. 排障

| 症状 | 最可能的原因 |
|---|---|
| 打开域名是 Nginx 欢迎页 | `nginx.conf` 没放进 `conf.d/`，或 server_name 没改 |
| 502 Bad Gateway | 应用没起来。`systemctl status kuke` / `docker compose logs` |
| 页面白屏，控制台报 CSP 错误 | 反代改了响应头。CSP 由应用下发，Nginx 不要覆盖 |
| 所有人被限流 | `TRUST_PROXY` 没配 —— 所有请求被当成同一个 IP |
| 学生说密码输对了还是登不进 | 连续失败触发了账号锁定。等 10 分钟，或让老师重置密码 |
| 静态资源 404，但 API 正常 | `web/dist` 没构建。`npm run build` |
| 磁盘被日志写满 | `LOG_LEVEL` 是 info。生产应该用 warn（代码里已按 NODE_ENV 默认） |
| AI 课堂逐字输出变成一次性全出来 | Nginx 缓冲了 SSE。检查 `/api/ai/` 的 `proxy_buffering off` |

看日志：

```bash
sudo journalctl -u kuke -f                    # systemd
docker compose logs -f kuke                   # Docker
sudo tail -f /var/log/nginx/kuke.error.log    # 反代层
```

## 8. 公网安全清单

上线前逐条确认：

- [ ] **5180 端口没有对公网开放**（安全组里只放 80/443）
- [ ] HTTPS 正常，`http://` 会 301 到 `https://`
- [ ] `NODE_ENV=production`（否则 cookie 不带 `Secure`）
- [ ] `TRUST_PROXY` 收窄到代理地址，**不是** `true`
- [ ] `KUKE_ALLOW_REGISTER` 是 0（或确认你要开放注册）
- [ ] `KUKE_PASSWORD` 已从环境变量里换成一个只存在于密码管理器里的值
- [ ] `/etc/kuke/env` 权限是 600 且属主是 root
- [ ] 备份在跑，且**验证过恢复流程**（没验证过的备份不算备份）
- [ ] 备份有异地副本
- [ ] `LOG_LEVEL=warn`
- [ ] 应用以非 root 用户运行
- [ ] 云主机开了自动安全更新（`unattended-upgrades`）

### 关于限流

这个项目对「学生都在机房、共用一个出口 IP」的场景做了专门处理：

- 业务接口按**用户**分桶（不是按 IP）—— 300 人共用出口也互不影响
- 登录按**失败次数**分桶（不是按请求数）—— 300 次成功登录不会被拦

所以**不要**为了「防刷」去 Nginx 层再加一道按 IP 的业务限流 ——
那会把机房场景重新打回「全班共用一张配额卡」的状态。
Nginx 层的 `limit_req` 只用来挡连接层攻击（模板里已经配好）。

## 9. 性能：这台机器能撑多少人

实测数据（8 核 Mac，本机压测，300 并发虚拟用户跑完整学习动线）：

| 场景 | 吞吐 | 成功率 | p95 |
|---|---|---|---|
| 只读接口 | 4721 req/s | 100% | 71ms |
| 完整动线（独立 IP） | 213 req/s | 100% | 3ms |
| 判题提交 300 并发 | 见 `bench/` | — | — |

**结论：2 核 2G 撑 300 人是够的**，前提是：

- 判题是低频动作（一个学生几分钟才交一次卷），不是持续压力
- 真正的尖峰只有两个：**开学第一课同时登录**、**下课前一分钟同时交卷**
- 这两个尖峰靠「登录失败计数 + 参考答案缓存」已经能扛住

要留更多余量，按顺序做这三件事：

1. `UV_THREADPOOL_SIZE=16`（systemd 模板里已经加了）—— 登录 p95 从 1.4s 降到 400ms 级
2. 多起两个 Node 进程（`cluster` 或两个 systemd 实例共享端口）
3. 判题服务拆成独立进程，别和 API 抢 CPU

自己压一遍：

```bash
node bench/run.mjs session --c 300 --dur 60 --ip same
node bench/bench-submit.mjs submit --c 300 --dur 20 --level L01
```

详见 `bench/README.md`。
